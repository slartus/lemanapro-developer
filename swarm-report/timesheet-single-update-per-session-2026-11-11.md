# Таймшит: обновление раз за сессию + TTL-кэш Tracker-данных

Дата: 2026-11-11

## Задача

Таймшит обновлялся при каждом входе на страницу. Ожидался «редирект на неделю», триггерящий обновление — его не оказалось.

## Диагноз

Редиректа нет. Цепочка: навлинк «Таймшит» (`base.html:156`, `href="/timesheet"` без `?week=`) → полная перезагрузка страницы → `init()` → безусловный `load()` → `GET /api/timesheet` без недели → бэкенд подставляет текущую неделю и пересобирает данные. `history.replaceState` пишет `?week=` в URL после загрузки — визуально похоже на редирект, но запросов не дублирует. Основная нагрузка: `_tracker_data` (search_my_issues + search_worklogs + get_issues) ходил в Tracker на каждый запрос без кэша.

## Решение (оба пункта согласованы)

### 1. Клиентский guard «раз за сессию» — `timesheet.js`

- `sessionStorage`-кэш payload (`lpdev:timesheet:payload`, TTL 12 ч).
- Повторный вход: гидрация из кэша без запроса + статус «Данные из этой сессии — „Обновить" загрузит свежие».
- Гидрация только если кэш совпадает с неделей из URL или с текущей ISO-неделей (защита от «застрял на старой неделе»).
- Каждая сетевая загрузка обновляет кэш сессии.
- Новая кнопка «Обновить» в тулбаре (`refresh-week`) — ручное обновление, `disabled` пока нет данных.

### 2. Бэкенд TTL-кэш `_tracker_data` — `timesheet_routes.py`

- `TRACKER_DATA_TTL_SEC = 300`, `TRACKER_DATA_CACHE_SIZE = 8`.
- Ключ: (начало недели, конец недели, today, отсортированные ключи задач).
- Ошибки Tracker не кэшируются (следующий запрос повторяет попытку).
- Инвалидация: смена конфига Tracker (`tracker_for`) и после записи (`api_timesheet_submit`).

## Совместимость с правилами GitLab/Tracker API

Запросы остаются on-demand: и кэши работают только по действию пользователя (открытие страницы, кнопка «Обновить»). Объём запросов к Tracker сокращается с «каждый вход на страницу» до «раз в 5 минут максимум» + ручные обновления.
