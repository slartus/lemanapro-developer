# lemanapro-developer — MVP (E0–E4), 2026-11-09

## Задача
Объединить mr-watch (авторевью MR) и gitlab-mr-radar (Chrome-расширение) в один локальный сервис с веб-страницей: выдвижное меню слева, общие запросы к GitLab, без расширения и без уведомлений. По ходу пользователь выбрал одну общую таблицу MR вместо двух разделов.

## Решения
- Основа — mr-watch (история сохранена), radar влит `git subtree` в `radar/` с историей. Пакет `mrwatch` → `lpdev`.
- Логика radar осталась на JS и запускается бэкендом как node-подпроцесс (`radar/src/runner.mjs`); в GitLab ходит только через прокси `/gl/*` с секретом процесса, PAT не покидает Python. Общая пауза на 429 и лимит параллельности для поллера и радара.
- В таблицу `mr` пишет только поток ревью; радар хранит снимок в `radar_snapshot` (схема v12). Строки таблицы объединяются во фронте по `project_id!iid`.
- Анализ на реальных данных: 10 из 10 открытых MR есть в обоих инструментах — одна таблица вместо двух экранов.

## Сделано
- E0: репо, переименование, CI (pytest, ruff, node), `deploy/migrate-from-mr-watch.sh`.
- E1: выдвижное сворачиваемое меню, проверка Origin/Sec-Fetch-Site для изменяющих запросов.
- E2: GraphQL/REST-прокси с allowlist, только чтение (мутации и батчи `_json` отклоняются), общая пауза 429.
- E3: `RadarScheduler` (интервал, быстрый режим при идущем CI ≤ 1 ч, коалесцирование пробуждений, устойчивость к падениям node), `/api/radar`.
- E4: общая таблица MR (5 колонок, чипы-фильтры, «Требуют действия» по умолчанию, snooze, свёрнутые блоки задач/возможных MR/сломанных веток, счётчик в меню и в title, точка на favicon для завершённых ревью).

## Проверка
- pytest 762 (покрытие 93%), node radar 142, node таблица 11 — зелёные.
- Сквозной тест: настоящий node → прокси на uvicorn → фейковый GitLab.
- Превью на реальных данных (копия БД mr-watch + последний снимок radar из Chrome) — скриншоты desktop/mobile.
- Каждый этап — отдельное ревью агентом code-reviewer с итеративными правками до вердикта без MAJOR+ (в E2 найден и закрыт BLOCKER: мутации через `_json`).

## E5–E6 (сделано после MVP)
- E6: списки MR, которые радар получает через прокси, идут в поток ревью через `Poller.ingest` (тот же путь, что sweep: `_upsert` + `_reconcile`), только если данные новее сохранённых. Любой upsert игнорирует данные старше сохранённых (медленный sweep не откатит head); todo с устаревшим detail не теряется, а повторяется. Изменение MR, замеченное поллером, будит радар (не чаще раза в минуту), в т.ч. после рестарта.
- E5: кнопки «▶ Ревью» / «↻» в таблице; `POST /api/mr/{pid}/{iid}/review` перечитывает MR из GitLab и ставит ручное ревью на текущий head.
- Ревью агентом: найден MAJOR (молчаливая потеря todo из-за новой защиты от устаревших данных) — исправлен и покрыт тестом.
- Тесты: pytest 803 (покрытие 93%), node 142 + 11.
