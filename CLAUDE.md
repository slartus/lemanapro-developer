# Правила проекта

## GitLab API — экономия запросов

Принцип: сервис работает on-demand, фонового опроса GitLab нет. Любое изменение, добавляющее
запросы в GitLab, проверяется по этому списку.

- Никакого периодического фона: poller и radar запускаются только по действию пользователя
  (открытие страницы, кнопка «Проверить/Обновить»). `gitlab.poll_interval_sec` и
  `radar.interval_minutes` = 0 означают «выключено».
- Автостарт ревью запрещён: новые PR/пуши не отслеживаются, ревью запускается только кнопкой
  (`POST /api/mr/{p}/{iid}/review`). Пуш нового коммита не отменяет и не переоткрывает
  запущенное ревью (supersede удалён); отмена ревью — только вручную.
- Новые фичи — только on-demand: запросы по действию пользователя, с кэшем (TTL или бессрочный)
  и дедупликацией между вкладками/страницами. Медленное — в фоне задачи, а не в блокирующем
  запросе.
- Предпочитать пакетные и групповые запросы одиночным: `GET /groups/:id/merge_requests` вместо
  N пер-проектных, GraphQL-батчи (states/pipelines/verdicts) вместо циклов REST, списочные
  эндпоинты вместо fetch по одному объекту.
- Полные сканы (все MR проекта, notes по каждому MR) — одноразовые, с меткой в `poll_state`;
  не повторять после рестарта процесса без сброса метки.
- Не обходить защиту клиента: 429/Retry-After, паузы, семафор и пагинационные капы в
  `gitlab_client.py` не снимать и не увеличивать лимиты запросов.
- Изменение, добавляющее GitLab-запросы, обязано в описании коммита/CHANGELOG указывать:
  триггер (что запускает), частоту, оценку объёма (req/день при типичном использовании).
