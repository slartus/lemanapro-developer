# lemanapro-developer

Локальная страница разработчика для self-hosted GitLab. Объединяет два инструмента:

- **авторевью MR** (бывший mr-watch) — описан ниже;
- **радар MR** (бывший gitlab-mr-radar, каталог `radar/`) — секции «на ревью», «назначены», «упомянули», «ждут апрува», «треды», «мои MR», «возможные MR», «сломан default branch». Логика на JS, запускается бэкендом; тесты — `cd radar && node --test`.

Главная страница — общая таблица MR: в строке и данные радара (роль, CI, апрувы, треды, merge-статус), и авторевью (статус, вердикт, находки). Секции радара — фильтры-чипы, по умолчанию «Требуют действия». Задачи с упоминанием, возможные MR и сломанные default-ветки — свёрнутые блоки под таблицей. Настройки радара — секция `radar:` в конфиге.

### Разработка и выкатка

Сервис работает из `~/projects/lemanapro-developer` (шаблоны и статика читаются с диска на каждый запрос), поэтому правки в этой папке не делаются. Разработка — в отдельном worktree (`git worktree add ../lemanapro-developer-dev -b <ветка>`), выкатка — `deploy/update.sh <ветка>` из worktree: fast-forward рабочей копии, `pip install -e .`, перезапуск LaunchAgent, проверка `/healthz`. Незавершённые ревью после перезапуска возвращаются в очередь.

### Переход с mr-watch

1. Остановить mr-watch и выгрузить его LaunchAgent: `launchctl unload -w ~/Library/LaunchAgents/ru.slinkin.mr-watch.plist`, plist убрать из `~/Library/LaunchAgents`.
2. `deploy/migrate-from-mr-watch.sh` — копирует БД (`data/lpdev.db`) и конфиг с новыми путями. Бэкапы mr-watch не переносятся.
3. `deploy/install.sh`.

## Авторевью

Локальный сервис автоматического ревью merge request для self-hosted GitLab.
Следит за MR, где вы упомянуты, назначены ревьювером/исполнителем или являетесь
автором, и прогоняет их через [opencode](https://opencode.ai) с read-only
агентом ревью. Результаты — в локальной базе и веб-UI, в GitLab ничего не
пишется (ни комментарии, ни отметки todo).

## Как работает

Сервис работает **on-demand**: фонового опроса GitLab нет. Обновление таблицы и
радара происходит при открытии главной страницы и по кнопке «Проверить сейчас»
(с дедупликацией: не чаще раза в минуту для таблицы и двух минут для радара;
запускаются в фоне, не блокируя отрисовку из локальной базы). Ревью
запускается только кнопкой в таблице. Групповые проекты с общим namespace
опрашиваются одним запросом `GET /groups/:id/merge_requests`.

- **Poller** на каждый тик (по открытию страницы или кнопке):
  - читает pending-todo (`/todos`); обработанные todo запоминаются локально
    (таблица `todo_seen`), в GitLab не помечаются;
  - при первом появлении проекта делает фулскан открытых MR
    (`/projects/:id/merge_requests`), ищет упоминания в описании и заметках;
  - дальше — sweep по `/projects/:id/merge_requests?updated_after=<курсор>`
    с отдельным курсором на каждый проект (перекрытие 2 мин);
  - разово добирает роли (`ревьюер/упомянули/назначен/мой`) для уже
    известных MR.
  Авто-ревью по триггерам (todo, новый MR, push, Ready) удалено: эти сигналы
  обновляют таблицу, но ревью ставится только кнопкой.
  MR в статусе draft автоматически не ревьюится. При переводе MR в draft
  активные ревью (`queued`/`cloning`/`reviewing`) отменяются (`cancelled`);
  новый коммит в draft отменяет устаревшее ревью, но нового не ставит.
  Ручной Re-review для draft работает.
  Если в MR пришёл новый коммит, пока ревью по старому head ещё идёт
  (`cloning`/`reviewing`), оно отменяется (статус `cancelled`, процесс
  останавливается, клон удаляется) и на новый head ставится ревью `push` —
  всегда, независимо от `re_review_on_push`, но только для открытого MR.
  Ревью в очереди (`queued`) просто переносится на новый head; завершённые
  (`done`/`error`) не трогаются. Отменённое ревью можно перезапустить (Re-review).
  Debounce: ревью `push` и перенос ревью из очереди на новый head
  откладывают старт на `review.push_debounce_sec` (по умолчанию 120 с, 0 —
  без отсрочки), каждый следующий push отодвигает его снова — серия push'ей
  даёт одно ревью по устоявшемуся head. Ревью `new` (todo, ревьюер, Ready) и
  ручной Re-review не откладываются.
- **Worker'ы** (`review.max_parallel`, по умолчанию 2) берут ревью из очереди в
  SQLite и до клона сверяют `head_sha` ревью с текущим head MR в GitLab
  (закрывает рестарт с ревью на старом коммите и пропущенную poller'ом смену
  head). Если head ушёл: MR закрыт/смержен или в draft — ревью `cancelled`;
  иначе ревью переносится на новый head и возвращается в очередь с той же
  отсрочкой `push_debounce_sec` (если на новый head уже есть такое ревью —
  `cancelled`). Дальше — shallow-клон ровно на `head_sha` ревью, base-ветка в
  `refs/lpdev/base`, diff `git diff <base_sha> <head_sha>` (base —
  `diff_refs.base_sha` MR, а если head MR ушёл вперёд — merge-base с
  `refs/lpdev/base`), затем `opencode run` с агентом проекта. После ответа,
  до удаления клона, сервис сам вырезает код к находкам по `путь:строка`:
  hunk диффа ±6 строк, а если строки нет в диффе — ±4 строки файла из клона.
  Ошибки клона — до 3 попыток с бэкоффом; если head MR уехал —
  ревью переносится на новый head. При свободном месте < 5 ГБ ревью не
  запускается. К Re-review можно приложить доп. инструкции (до 2000
  символов): они идут в промпт отдельной секцией после правил и до данных MR
  и сохраняются при переносе ревью на новый head.
- **Вопросы ревьюеру**: на странице завершённого ревью (`done` с сессией
  opencode) можно задать вопрос (до 4000 символов, до 50 на ревью, по одному
  за раз). Отдельный worker клонирует `head_sha` ревью в тот же каталог, что
  и ревью, и запускает `opencode run --session`: первый вопрос — форк сессии
  ревью (`--fork`), следующие продолжают сессию предыдущего ответа. Таймаут —
  `review.question_timeout_sec` (600 с), лог — `logs/question-<id>.log`.
  Пока вопрос в работе, Re-review запрещён. После Re-review старые вопросы
  показываются свёрнутыми «к предыдущей версии ревью». Если коммита ревью
  больше нет в репозитории, вопрос завершается ошибкой.
- **Веб-UI** на `http://127.0.0.1:8123`: таблица открытых MR (закрытые и
  смерженные не показываются, сортировка по последней активности в GitLab) с
  ролями (`ревьюер/упомянули/назначен/мой`), draft, вердиктом, счётчиками находок и
  свежестью активности (подсветка > 3 и > 7 дней); фильтры по статусу, роли,
  «требуют правок»; бейдж «упомянули» ведёт на комментарий с
  упоминанием. Автообновление через `/api/mrs` и `/api/reviews/{id}`: 5 с при
  активных ревью, иначе 30 с, в скрытой вкладке — раз в 60 с; ревью, завершившиеся
  (`done`/`error`) пока вкладка скрыта, показываются счётчиком `(N)` в заголовке
  вкладки и красной точкой на favicon, сброс — при возврате на вкладку; после «Проверить
  сейчас» — быстрые обновления через ~2 и ~6 с. Страница ревью — текст ревью
  (пропорциональный шрифт, markdown-заголовки, inline code, fenced-блоки
  модели — как код с подписью языка), код к находке сразу после её строки
  (несопоставленные — внизу, «Код к находкам»), кнопка «Развернуть весь код» и
  Re-review (берёт текущего агента проекта). `/settings` — правка параметров
  ревью и проектов (проект задаётся ссылкой или slug), «Проверить сейчас» —
  перечитать конфиг и опросить GitLab сразу (без кулдауна).

## Таймшит

Вкладка `/timesheet` (по мотивам [timesheeter](https://github.com/diarworld/timesheeter)):
таблица на ISO-неделю с предложениями, сколько времени списать в задачи Yandex
Tracker, и кнопка «Списать» (worklog в Tracker). Аналитики нет.

**Настройка** (`tracker:` в конфиге, через `/settings` не меняется):

```bash
# OAuth-токен Tracker (scope: tracker:read + tracker:write) — в Keychain
security add-generic-password -s lpdev -a tracker -w
```

```yaml
tracker:
  enabled: true
  submit_enabled: true          # без него — только просмотр
  org_id: "<ID организации>"
  org_header: X-Org-Id          # Яндекс 360; для Yandex Cloud Organization — X-Cloud-Org-Id
  token_command: security find-generic-password -s lpdev -a tracker -w
  queues: [SUPERAPP]            # пусто — любые очереди
```

Без `tracker.enabled` страница работает только на данных GitLab (без «уже
списано» и без кнопки «Списать»). Применяется после «Проверить сейчас» или
рестарта.

**Роль** — `tracker.role`: `developer` (по умолчанию) или `qa`. Роль меняет
статусы «в работе» по умолчанию и веса (см. «Алгоритм»); явно заданные
`in_progress_statuses` и `activity_statuses` важнее роли.

| Роль | `in_progress_statuses` | `activity_statuses` |
|------|------------------------|---------------------|
| `developer` | `development, codereview, rework` | `d`, `r`, `w` |
| `qa` | `testing` | `testing` → `t` |

**Только таймшит, без сервиса** (например, для тестировщика): `pip install -e .`,
затем `LPDEV_CONFIG=<путь к config.yaml> lpdev timesheet` — поднимает только
`/timesheet` на `127.0.0.1:8123` (`--port`), открывает браузер
(`--no-browser` — не открывать), работает до Ctrl+C. Поллер, радар, авторевью
и opencode не запускаются, LaunchAgent не нужен, `projects:` в конфиге можно не
указывать; нужны `gitlab:` (PAT — для событий своих push и MR) и `tracker:`.
`/settings` и страница MR в этом режиме недоступны, конфиг правится руками,
изменения применяются после перезапуска. **`paths:` обязателен и должен
указывать на свою папку**: по умолчанию пути ведут в БД основного сервиса.
Проекты авторевью в этом режиме в БД не синхронизируются, `/healthz` не
показывает состояние опроса.

```yaml
gitlab:
  url: https://gitlab.lmru.tech
  pat_command: security find-generic-password -s lpdev -a gitlab -w
tracker:
  enabled: true
  submit_enabled: true
  role: qa
  org_id: "<ID организации>"
  token_command: security find-generic-password -s lpdev -a tracker -w
  queues: [SUPERAPP]
paths:
  db: ~/lpdev/lpdev.db
  workspaces: ~/lpdev/workspaces
  logs: ~/lpdev/logs
```

**Готовая сборка для QA** (`deploy/qa/`): `build.sh` собирает PyInstaller-бинарь
(one-dir, arm64, ad-hoc codesign) и складывает в `dist/lpdev-qa-<arch>-<commit>.zip`
бинарь, `Lemanapro Timesheet.command` (двойной клик) и `INSTALL.md` с инструкцией
для тестировщиков; печатает commit и sha256 для публикации. Бинарь `lpdev-qa`
(`lpdev.qa_main`) при первом запуске проводит мастер настройки (GitLab URL, PAT
`read_api`, org_id, очереди, «Списать?», OAuth-токен `y0_…`, порт; токены — в
Keychain `lpdev-qa`, конфиг `~/.config/lpdev-qa/config.yaml` 0600, роль `qa`,
данные в `~/lemanapro-timesheet/`), затем запускает только `/timesheet` на
127.0.0.1:8124 и открывает браузер. Повторный запуск гасит предыдущий экземпляр
по pidfile (рядом с БД) и открывает свежую вкладку; Ctrl+C останавливает сервис
и best-effort закрывает вкладку браузера (osascript, при отказе — вручную);
`--setup` — перезапуск мастера, `--port` — порт.

**Источники:**
- GitLab: мои события (`GET /api/v4/events`, кэш 5 минут) за неделю.
  - Push: ключ из ветки, затем из заголовка коммита, затем из MR этой ветки.
    MR ищется в локальной БД, среди MR из
    событий недели (`GET /projects/:id/merge_requests/:iid`), затем
    `GET /projects/:id/merge_requests?source_branch=<ветка>&state=all` (кэш
    10 минут). Не считаются: push в default-ветку проекта и в
    `tracker.ignored_push_branches` (fnmatch, по умолчанию `develop`, `main`,
    `master`, `release/*`, `rc/*`), merge-коммиты (`Merge branch …`,
    `Merge remote-tracking branch …`) из одного коммита, удаление веток и
    теги. Push merge-коммита с несколькими коммитами считается без
    merge-коммита (вес по `commit_count − 1`), ключ из его заголовка не берётся.
  - Ключ MR (для событий MR и push в его ветку): заголовок MR → ветка MR →
    ссылка на MR в комментариях задач Tracker → описание MR. В описании
    принимаются только явные формы `Closes|Fixes|Resolves|Closed|Fixed|Resolved
    KEY` и `(KEY)`, голые упоминания игнорируются. Описание берётся из ответа
    API, если MR и так догружался (в локальной БД описания нет).
  - Ссылки из Tracker (только при `tracker.enabled`): мои задачи, обновлённые
    с начала недели минус 7 дней (не больше 49, по одному запросу комментариев
    на задачу, кэш 10 минут), ссылки вида `<gitlab.url>/<проект>/-/merge_requests/<iid>`
    (с любыми суффиксами) из комментариев любого автора, только с хоста
    `gitlab.url`. Если MR указан в нескольких задачах: побеждает комментарий
    `tracker.pr_link_bots` (по умолчанию `ya360-pr-check`), иначе задача,
    назначенная на меня; если однозначно не выбрать — ссылка не используется.
    Ошибки чтения пропускают источник (warning в логе).
  - Открытие MR — всегда моё. Мерж, апрув и комментарии считаются только в
    моих MR (автор MR — из БД или `GET /projects/:id/merge_requests/:iid`,
    я — из `GET /user`); если автора или меня определить не удалось, событие
    не учитывается (warning в логе; если не удалось определить меня — ещё и
    предупреждение в `warnings` ответа, повторная попытка через минуту).
    Комментарии вне MR не учитываются. **Время на ревью чужих MR (апрувы,
    комментарии и мержи чужих MR) в предложения не попадает** — так решил
    пользователь; при необходимости его можно добавить вручную.
  - Неудачные запросы к GitLab (проект, MR, MR ветки) повторяются не чаще раза
    в минуту.
  - Ключ — `QUEUE-123` из `queues` (в ветках без учёта регистра). Своя работа
    без ключа (push, открытие/мерж своего MR) — строка «Без задачи», один
    элемент на ветку (название MR и ссылка, если MR найден): показывается, но
    не списывается. Комментарии и апрувы без ключа отбрасываются.
  - Не больше 50 запросов к GitLab на одну загрузку недели.
- Tracker: кандидаты «в работе» — задачи, которые сейчас на мне или ушли с
  меня с начала недели, и сейчас в статусах `tracker.in_progress_statuses` или
  ушли из них с начала недели (`Assignee: me() OR Assignee: changed(from: me()
  date: >= <пн>)` и `Status: <статусы> OR Status: changed(from: "<статус>" date:
  >= <пн>)`; пустой список статусов — `"Status Type": inProgress` по текущему
  состоянию), не больше 20. По истории статусов и исполнителя
  (`changelog?field=status`, `changelog?field=assignee`) для каждой считаются
  дни, когда задача была **моей**: в одном из этих статусов и с исполнителем
  «я». Нахождение в статусе меньше минуты (проход насквозь) не считается.
  Задача, не бывшая моей на этой неделе, строкой не становится. Если историю
  исполнителя прочитать не удалось — считается, что исполнитель «я»; если не
  удалось прочитать историю статусов — задача считается моей все дни недели,
  если сейчас она на мне и её текущий статус из списка. Так задача, ушедшая в тестирование во
  вторник, остаётся у разработчика в понедельник–вторник, а вернувшаяся в
  доработку снова становится его только с дня возврата. Время аналитиков и
  тестировщиков в той же задаче на расчёт не влияет (списанное считается только
  моё). Уже списанное мной (`POST /worklog/_search` с `createdBy` =
  `trackerUid`/`uid` из `/myself` и фильтром по `start` за неделю); названия
  задач. Задачи можно добавить вручную.

- Tracker, только для роли `qa`: в дни, когда задача была моей, — мои переходы
  статуса (автор записи changelog — я) и мои комментарии в ней (`createdAt`;
  комментарии перечитываются, только если у задачи изменился `updatedAt`).

**Активность задачи** (только отображение): у строки — интервалы дней, когда
задача была в статусах `tracker.activity_statuses`; для кандидатов «в работе» —
только пока была моей (см. выше), для остальных строк (например, ревью чужой
задачи) — независимо от исполнителя,
по истории `GET /issues/{key}/changelog?field=status` и `?field=assignee`
(пагинация по `Link`, не больше 10 страниц). Открытый интервал заканчивается сегодня, соседние и перекрывающиеся
интервалы одного статуса склеиваются, в ответ попадают только пересекающиеся с
неделей. Не больше 30 задач за загрузку, 6 запросов параллельно, кэш 10 минут;
при ошибке — пустой список и warning в логе.

**Алгоритм** (на каждый день): норма — 8 ч (`day_hours`) по производственному
календарю РФ (`src/lpdev/calendar/ru/<год>.json`: праздники, сокращённые на 1 ч
дни, рабочие выходные; для года без файла — Пн–Пт и `calendar_ok=false`).
Остаток = норма − уже списано − ручные правки, вниз до шага (`step_minutes`,
30 мин). Веса активности: push 3 (+1 за каждый коммит сверх первого, до 6),
открытие/мерж MR 2, апрув/комментарий в своём MR 1. Задачи «в работе»
учитываются только в дни, когда были моими. Роль `developer`: такие задачи без
активности в этот день — вес 0,5, суммарно не больше 25% остатка (если
активности нет совсем — весь остаток поровну), не больше 5 задач в день. Роль
`qa`: тестирование — основная работа, поэтому каждый день, когда задача была
моей, даёт ей вес 3 (как push), без ограничения 25%; плюс мой переход статуса 2
и мой комментарий 1 — тоже только в дни, когда задача была моей. Лимита на
число задач в день у `qa` нет. Доля меньше шага отходит самой тяжёлой задаче,
округление — метод наибольших остатков (сумма ровно равна остатку). В выходные
и праздники ничего не предлагается. Ручная правка ячейки — «сколько ещё
добавить», она фиксирована и в распределении не участвует.

**Списание:** с понедельника прошлой недели по сегодня (будущее и старые
недели — только просмотр), не больше 50 ячеек за раз, кратно шагу, итог дня не
выше нормы. Перед записью под блокировкой перечитывается уже списанное из
Tracker и журнал `worklog_submission`; повтор той же ячейки с теми же минутами
в течение 10 минут после успешной записи — `skipped`. Создание worklog не
повторяется автоматически: таймаут/5xx/обрыв → статус `unknown` и сверка по
worklog задачи; несверенные `unknown` проверяются при следующем списании этой
ячейки и при открытии недели (не больше 20 записей за раз, только если
Tracker включён и списание сейчас не идёт): найдено — `done`, и повторное
списание ячейки даёт `skipped`; не найдено и записи больше 2 минут — `failed`,
можно повторить. Пока сверка не прошла (Tracker недоступен), ячейка не
списывается (`unknown`). Если Tracker не вернул id worklog, запись тоже
сверяется. Время старта worklog — 09:00 в `tracker.timezone`, комментарий не
передаётся. В логах — только ключ, дата и минуты. Предложения строятся только
по сегодня включительно. Ведущий ключ задачи в названии (`SUPERAPP-1: …`)
срезается.

Блокировка списания работает внутри одного процесса, поэтому сервис
запускается одним воркером uvicorn (как в `deploy/`); несколько воркеров могут
дважды списать одну ячейку.

**Риски и допущения:**
- Tracker может отдавать длительность в днях/неделях (`P1D`, `P1W`) по своей
  норме; здесь 1D = `day_hours` часов, 1W = 5D. Если в организации другая
  норма дня, «уже списано» будет посчитано неверно.
- Списанное ищется по `createdBy` (uid) и `start`; день определяется по
  `start` в `tracker.timezone` (на клиенте фильтр повторяется). P1D = полный
  день подтверждён на реальных данных.
- Списанное другими людьми за меня и чужие worklog не учитываются.

## Безопасность

- opencode: `--pure`, **без** `--auto`; окружение — только `PATH`, `HOME`,
  `TMPDIR` и `OPENCODE_DISABLE_PROJECT_CONFIG=1`,
  `OPENCODE_DISABLE_CLAUDE_CODE=1`; PAT в окружение не попадает.
- Агенты — только глобальные (`~/.config/opencode/agent/` или `agents/`) и
  только read-only: перед каждым ревью frontmatter проверяется, `edit`, `bash`,
  `webfetch` должны быть запрещены (`tools: false` или `permission: deny`),
  иначе ревью падает с ошибкой. В `/settings` предлагаются только такие агенты;
  если их нет — предлагается `mr-watch-reviewer` по умолчанию (при запуске
  ревью он всё равно проходит проверку read-only).
- Клон: без hooks и LFS, `protocol.file.allow=never`,
  `transfer.fsckObjects=true`, `core.symlinks=false`; PAT отдаётся через
  временный `GIT_ASKPASS`, в URL и `.git/config` не попадает, remote после
  клона удаляется. Санитизация (без учёта регистра): в корне — `.opencode`,
  `opencode.json(c)`, `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, `.claude`,
  `.agents`; рекурсивно — `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`. Если что-то
  не удалилось — ревью падает.
- Код к находкам читается только внутри клона: путь без `..`, абсолютных
  путей и `.git` (в любом регистре, а также по inode каталога `.git`), открытие
  через `O_NOFOLLOW`, только обычные файлы ≤ 2 МБ, не бинарные; лимиты —
  30 находок, 40 строк / 4000 символов на фрагмент, 60 000 символов на ревью.
- Subprocess git/opencode: своя process group, таймаут (SIGTERM → SIGKILL),
  убийство группы при отмене, лимит вывода; `glpat-`/`Bearer`/`OAuth`/`y0_`
  маскируются в логах и ошибках.
- `gitlab.url` — только `https://`, без логина/пароля, query и fragment.
  Ссылки в UI проходят `safe_url` (только хост GitLab).
- Веб-UI: bind `127.0.0.1`, Host-check (`127.0.0.1:8123`/`localhost:8123`),
  все не-GET/HEAD/OPTIONS запросы требуют `X-Requested-With: lpdev` (CSRF,
  кроме внутреннего прокси радара `/gl/`, там — секрет), HTML с `no-store`.
- Конфиг: при group/other-writable или чужом владельце сервис не стартует,
  world-readable — warning; UI пишет конфиг и `.yaml.bak` с правами 0600.
  PAT — в macOS Keychain, в конфиге только `pat_command`.

## Установка

```bash
# 1. PAT в Keychain (scope: read_api + read_repository)
security add-generic-password -s mr-watch -a gitlab -w "<GITLAB_PAT>"

# 2. Агент ревью — в ~/.config/opencode/agent/ (см. «Агент ревью»)

# 3. Конфиг (install.sh создаст его из примера, если нет)
cp config.example.yaml config.yaml && chmod 600 config.yaml
$EDITOR config.yaml

# 4. Установка и запуск (venv + launchd)
./deploy/install.sh
```

Проверка: `curl http://127.0.0.1:8123/healthz`, UI — http://127.0.0.1:8123

## Конфиг

Путь — `$LPDEV_CONFIG`; launchd-plist задаёт `<проект>/config.yaml`, без
переменной — `~/.config/lemanapro-developer/config.yaml`. Поля — в `config.example.yaml`:
GitLab (URL, `pat_command`), проекты (`gitlab_project_id`, `slug`,
`agent`, опционально `model`/`variant`), ревью
(параллельность, таймаут, глубина клона, TTL workspaces и логов, отсрочка
ревью после push `push_debounce_sec`), opencode
(`bin`, `model`, `variant`, `length_retry_variant`), радар, Tracker для
таймшита (см. «Таймшит»), пути.

Если модель упёрлась в лимит вывода (`reason=length`) и не выдала текста, ревью
автоматически повторяется с `opencode.length_retry_variant` (по умолчанию
`low`, `null` — без повтора) в пределах того же таймаута.

Изменение `max_parallel` через UI применяется только после рестарта.

## Агент ревью

Агенты живут вне репо, в `~/.config/opencode/agent/<имя>.md`:
`mr-watch-reviewer` (общий, по умолчанию), `lmwork-reviewer` (LMWork),
`platformeco-reviewer` (BFF-каналы Platformeco). Требования:

- frontmatter запрещает `edit`, `bash`, `webfetch` (иначе агент отклоняется);
- находки — строками списка `- [BLOCKER|MAJOR|MINOR|NIT] путь:строка — ...`:
  ссылка `путь:строка` (или `путь:от-до`) от корня репо сразу после маркера
  уровня, код не цитировать — его подставит сервис;
- блок исправления — только для BLOCKER/MAJOR, ≤ 5 строк, не больше 3 на ревью;
- критерии уровней явные: BLOCKER — auth, утечка токена/секретов, инъекции,
  потеря данных, падение, поломка контракта;
- в конце секция `## Verdict` с одним из `APPROVE`, `APPROVE_WITH_NITS`,
  `REQUEST_CHANGES` (или строка `Verdict: ...`); есть BLOCKER или MAJOR →
  `REQUEST_CHANGES`.

Счётчики уровней, вердикт и привязка кода разбираются одним парсером с общими
правилами: строки по `\n` (с отбросом `\r`), содержимое fenced-блоков и цитат
(`>`) игнорируется.

## Эксплуатация

```bash
launchctl load|unload ~/Library/LaunchAgents/ru.slinkin.lemanapro-developer.plist
tail -f logs/app.log                      # основной лог
tail -f ~/Library/Logs/lemanapro-developer/err.log   # stdout/stderr launchd (out.log/err.log)
curl -s http://127.0.0.1:8123/healthz     # status, last_poll, last_error, dead_tasks
```

- `/healthz`: 200 `ok`; 503 `degraded`, если последний опрос упал или умерла
  фоновая задача (поллер/воркер/бэкап — в `dead_tasks`).
- БД: `data/lpdev.db` (SQLite WAL, миграции через `PRAGMA user_version`).
  Бэкап раз в сутки в `data/backups/` (при старте — сразу, если последний
  старше суток), хранится 7.
- Логи: `logs/app.log` (ротация 5 × 5 МБ), `logs/review-<id>.log` — удаляются
  при старте старше `review.log_ttl_days`.
- Workspaces клонов: `workspaces/` — удаляются после ревью; старше
  `review.workspace_ttl_days` чистятся при старте. Временные askpass-скрипты —
  в `tmp/`, чистятся при старте.
